## R1. 同步機制：WebSocket（只推送）＋ HTTP（所有操作）

**決定**：

- **伺服端推送**：每個頁面開一條 WebSocket，只用來接收伺服端推送的「依角色裁切的完整快照」。
- **操作**：建立、加入、開輪等所有操作，一律走 HTTP POST。

**理由**：

- **同一瀏覽器的連線數上限**：本專案以「同一台電腦、多個瀏覽器分頁」模擬老師與各組。SSE（EventSource）走 HTTP/1.1，瀏覽器對同一個 host 最多只開 6 條連線。老師 + 5 組就用完了，第 6 組的分頁會卡住，連一般的 API 請求也會被排隊。WebSocket 不受這個限制。
- **操作走 HTTP**：可以直接用狀態碼表達錯誤，用 `Idempotency-Key` 標頭做重送去重（R5），也容易用 FastAPI `TestClient` 測試。WebSocket 只推送不接收指令，協定簡單。
- **推送完整快照，不推差異**：一個活動的資料量很小（幾十組、幾十題），推完整快照讓「重連後取得最新完整狀態」（FR-028）和平常更新走同一條路，不會有差異遺漏的問題。
- **斷線偵測**：前端在 WebSocket `close`／`error` 時立刻顯示「同步中斷」，並以退避（0.5、1、2、4 秒，最多 4 秒）重連。伺服端每 10 秒送一次 `ping` 訊息，前端超過 25 秒沒收到任何訊息，也視為中斷。

**考慮過的替代方案**：

- **SSE + HTTP**：伺服端較簡單，瀏覽器也會自動重連，但會碰到上述 6 條連線的上限。用不同主機名稱（`localhost`／`127.0.0.1`）可以繞過，但太脆弱，因此不採用。
- **WebSocket 雙向（操作也走 WebSocket）**：去重、錯誤碼、測試都要自己設計，增加複雜度（原則 VII），因此不採用。
- **輪詢**：2 秒內同步需要每秒輪詢，N 組時負擔大，延遲也不穩定，因此不採用。

## R2. 效能驗證組數 N 與量測方法

**決定**：

- **N = 6**：效能驗證以「老師 + 6 組」為準。自動化效能測試每組開 2 條連線，模擬多裝置同組，共 13 條 WebSocket。
- **量測起點**：後端在套用狀態變更的那一刻（取得活動鎖、狀態機回傳成功之後），把 `changedAt`（後端時間，毫秒）寫進快照。
- **自動化量測**（`tests/perf/`）：以真實 uvicorn 伺服器（本機）和 13 個 WebSocket 客戶端，量測「送出操作 → 每個客戶端收到含新版本的快照」的時間。開輪、關輪、定案、結束各做 10 次，**最大值**必須 < 2 秒。
- **人工量測**：頁面右下角顯示「狀態版本」與「延遲」，延遲 = 頁面完成畫面更新時的時間 − `changedAt`。後端與瀏覽器在同一台電腦，時鐘相同，可以直接相減。非實作者用老師 + 2 組分頁操作，記錄每次的版本與延遲。

**理由**：

- 一般課堂分 4～8 組，N = 6 取中間值。
- 自動化測試量到「收到快照」為止，人工量測補上「畫面更新」這一段。兩者合起來，就涵蓋 spec 定義的起點與終點（Q-10 內部決定）。
- 組數上限仍不自訂（Q-07）：N 只是驗證規模，不是系統限制。

**考慮過的替代方案**：

- **N = 2**（spec 的最低值）：太保守，無法反映一般課堂的組數。
- **在瀏覽器自動化工具裡量測畫面更新**：需要額外安裝瀏覽器驅動，增加環境依賴，因此不採用；改為人工驗證時讀取頁面上的延遲顯示。

## R3. lint、格式化與型別檢查

**決定**：

- **Ruff**：lint 用 `ruff check`，格式化用 `ruff format`，規則集為 `E, F, W, I, N, UP, B, D, ANN`。
  - D 是 docstring，採 Google 風格；ANN 是型別提示。
  - `tests/` 排除 D、ANN。
- **mypy**：檢查 `src/`，設定 `disallow_untyped_defs = true`。

**理由**：

- Ruff 一個工具同時做 PEP 8 檢查、import 排序與格式化，速度快、設定集中在 `pyproject.toml`。
- 規則 D、ANN 直接檢查憲章「公開函式要有型別提示與 docstring」。
- mypy 確認型別提示是正確的，而不只是有寫。

**考慮過的替代方案**：

- **flake8 + black + isort**：要裝三個工具、維護三份設定，因此不採用。
- **pylint**：較慢，預設規則也較吵，因此不採用。

**後續**：依憲章技術限制 2，這項定案要以修訂程序補回憲章（PATCH 版本），見 plan 的 Next Actions。

## R4. 測試工具與時間控制

**決定**：

- **測試框架**：pytest，搭配 FastAPI `TestClient`（含 WebSocket 測試）與 `pytest-timeout`。效能測試另用 `websockets` 客戶端連真實伺服器。
- **核心的時間**：核心函式一律接收 `now: datetime` 參數。單元測試直接傳入固定時間，例如 `now = 開輪時間 + 59 秒`、`+ 60 秒`，測截止前後，不用等待。
- **外層的時間**：
  - **`Clock`**：協定，正式環境實作是 `SystemClock`，測試用 `FakeClock`，可手動推進時間。
  - **`CountdownScheduler`**：協定，正式環境實作是 `AsyncioCountdownScheduler`（`asyncio` 任務等到截止時間），測試用 `ManualScheduler`，由測試呼叫 `fire(code)` 立即觸發。
- **「手動關輪與倒數同時」的測法**：
  1. **核心層**：對同一個 `Activity` 連續兩次 `apply(關輪)`，第二次必須回傳「已關輪、不改變狀態」。
  2. **服務層**：用 `asyncio.gather` 同時送出 `close_round(老師)` 與 `ManualScheduler.fire()`，重複 50 次（SC-003），確認結果只有 1 份、狀態版本只加 1。
- **測試與 Scenario 的對應**：每個測試函式的 docstring 第一行寫 `Scenario: US{n}-AS{m}`；`tests/` 底下另有一份對照表，由 tasks 階段產生。
- **架構測試**：`tests/architecture/test_core_is_pure.py` 用 `ast` 掃描 `src/lecture_quiz/core/`。核心不得匯入 `fastapi`、`starlette`、`asyncio`、`socket`、`time`，也不得呼叫 `datetime.now`／`utcnow`／`today`；任何其他 `lecture_quiz` 套件都不得被核心匯入。

**理由**：

- 時間由呼叫端傳入，是憲章架構限制的要求，也讓倒數測試快速且結果穩定。
- 用 `ast` 掃描不需要額外工具，又能自動守住「相依只能由外層指向核心」。

**考慮過的替代方案**：

- **freezegun**：需要修改全域時間，而且會掩蓋「核心有偷呼叫系統時鐘」的違規，因此不採用。
- **import-linter**：功能完整，但多一個依賴；目前只有一條規則，用 `ast` 測試就夠了，因此不採用。

## R5. 身分保存與重送去重

**決定**：

- **老師身分**（⚠ 提案相依 Q-04）：建立活動時，後端產生 32 bytes 的隨機 token（`secrets.token_urlsafe`）。前端存在 `localStorage`，key 是 `teacher:{活動代碼}`。
  - 同一瀏覽器的所有分頁共用這個 token。換瀏覽器或換裝置就沒有，因此拿不到老師身分。
  - 請求時以 `Authorization: Bearer <token>` 送出。
- **裝置身分**：加入組別時，後端產生裝置 token。前端存在 `sessionStorage`，key 是 `device:{活動代碼}`。
  - `sessionStorage` 每個分頁獨立，重新整理後仍在。這樣同一瀏覽器的多個分頁可以模擬不同組的裝置，而重新整理時身分會恢復（FR-012）。
  - 已知取捨：關掉分頁再開就會失去身分，這時要重新加入。同組其他裝置畫面上看得到憑證（⚠ 提案相依 Q-06），所以重新加入很容易。
- **活動代碼與組別加入憑證**（⚠ 提案相依 Q-06）：都由 `secrets.choice` 從 32 個字元中產生 6 碼。字元集是 `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`，排除 0、O、1、I。
  - 活動代碼產生時，要檢查不與存續中的活動重複。
  - 憑證只在同一組內使用，不需要全域唯一。
- **WebSocket 認證**：連線後，第一則訊息是 `{"type": "auth", "token": ...}`。token 不放在 URL，避免出現在存取紀錄裡。
- **重送去重**：
  - 前端在每次使用者操作時產生一個 UUID，放在 `Idempotency-Key` 標頭；重試時沿用同一個值。
  - 後端在活動內保存「(身分, key) → 原回應」，每個活動最多保留最近 1000 筆。
  - 建立活動還沒有活動可以存，所以另存在全域的「key → 活動代碼」表。
- **比對與日誌**：
  - 驗證 token 時，用 `secrets.compare_digest` 比對。
  - 日誌只記錄活動代碼、操作類型、結果、狀態版本，不記錄任何 token 或憑證（技術限制 3）。

**理由**：

- `localStorage` 與 `sessionStorage` 的差別，剛好對應「老師跨分頁共用、學生每個分頁是一台裝置」。
- 隨機 token 由後端產生並在後端驗證，前端不能偽造身分（原則 IV）。

**考慮過的替代方案**：

- **HttpOnly Cookie**：比較能防 XSS，但 cookie 會被同一瀏覽器的所有分頁共用，同瀏覽器就沒辦法模擬多組學生，因此不採用。前端以 `textContent` 輸出所有不可信文字，避免 XSS（原則 V）。
- **以組名當身分**：違反「不能只靠同名冒用」，因此不採用。

## R6. 同一活動的操作序列化

**決定**：

- **單一 process**：uvicorn 只開 1 個 worker，所有活動都在同一個 asyncio 事件迴圈中。狀態只存在記憶體，不能多 process（原則 VII）。
- **每個活動一把鎖**：每個活動各有一把 `asyncio.Lock`。服務層的每個會改變狀態的操作都依下列順序進行：
  1. 取得鎖。
  2. 取出目前的 `Activity`（不可變的資料）。
  3. 呼叫 `ActivityStateMachine.apply(activity, command, now)`。
  4. 成功時，以新的 `Activity` 取代舊的，並且狀態版本加 1。
  5. 釋放鎖。
  6. 推送快照。
- **關輪只一次的雙重保證**：
  1. 鎖保證兩個關輪請求依序執行。
  2. 狀態機看到 `round.closed == True` 時回傳 `AlreadyClosed`（成功但無變化），版本不加，也不推送。
- **倒數排程**：到期時以 `close_round(系統, now=clock.now())` 進入同一把鎖，和老師的手動關輪走相同路徑。老師先關輪時，取消排程任務；但即使沒取消成功，第 2 點也能保證不重複關輪。

**理由**：

- 不可變資料加上純函式，讓「舊狀態 + 操作 → 新狀態」可以單獨測試。
- 只用一把鎖就把並行問題限制在服務層，核心不用處理並行。

**考慮過的替代方案**：

- **所有活動共用一把全域鎖**：做得到，但一個活動的操作會阻擋其他活動，因此不採用。
- **actor／佇列**：對這個規模來說太重了（原則 VII），因此不採用。

## R7. 前端形式

**決定**：

- **頁面**：由 FastAPI 直接提供靜態檔，包括 `teacher.html`、`student.html`，以及原生 JavaScript（ES modules）與一份 CSS。不使用前端框架，也不需要建置工具。
- **不可信文字**：組名等文字一律以 `textContent` 輸出（原則 V）。

**理由**：

- 畫面只有兩頁、狀態都來自後端快照，原生 JavaScript 就足夠。
- 不用建置工具，助教 clone 下來就能跑（規章第 9 節「全新 clone 重跑」）。

**考慮過的替代方案**：

- **React／Vue**：需要 Node 與建置流程，增加環境依賴，因此不採用。

## R8. 002／003／004 還沒完成時的測試與展示

**決定**：

- **服務介面**：
  - 002 用的 `ActivityGateway`（`stage`、`is_teacher`、`replace_questions`），以及給 003／004 用的介面（見 [contracts/service-interfaces.md](contracts/service-interfaces.md)），都由 `ActivityService` 實作。
- **自動化測試**：直接呼叫 `replace_questions` 放入假題目。
- **人工驗證**（002 完成前）：以環境變數 `LECTURE_QUIZ_DEV_SEED=1` 啟用一個**只限老師**的開發用 API，`POST /api/dev/activities/{code}/seed-questions`，可放入 N 題假題目。
  - 預設關閉，quickstart 會註明。
  - 002 合併後移除，tasks 要列出這個移除任務。
- **定案**：細節屬於 004。001 先提供 `POST .../rounds/current/finalize`（只限老師，無其他前提），讓狀態機可以完整測試。004 實作時會在服務層加上自己的前提檢查，例如「判錯檢查已完成」，並把定案結果（已成功題、成功次數）透過 `finalize(outcome)` 傳入。

**理由**：

- 001 要能獨立驗收（spec 的 Independent Test），不能等 002～004 完成。

**考慮過的替代方案**：

- **等 002 合併後才做人工驗證**：這樣 001 會卡在相依上，因此不採用。
