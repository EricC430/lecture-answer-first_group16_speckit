# Feature Specification: 同一瀏覽器共用學生身分與跨分頁同步（Browser Identity Sync）

**Feature Branch**: `feature/36-007-browser-identity-sync`（Issue #36，從 `origin/main` 開出）

**Created**: 2026-11-26

**Status**: Draft

**Input**: User description: "補上一個已跟OpenSpec組核對的001內的功能: 使用瀏覽器cookies等網路資訊，同步同一瀏覽器內的身分和狀態，例如同個瀏覽器，學生不得同時開很多分頁，佔據他組的身分，提高這種意圖的實現困難度"

**OpenSpec Capability**: activity-session（基準檔 `docs/openspec-reference/activity-session/spec.md`）。本子功能是 **001-activity-session 的延伸**，修改 001 的「裝置身分」範圍：001 目前把**每個分頁**當成一台獨立裝置（001 研究 R5），本子功能改為**同一個瀏覽器的所有分頁共用一個學生身分**，做法比照 001 老師身分（FR-003、alignment 2026-11-23 C6）。

**與 OpenSpec 組的對齊**：使用者回報此行為已與 OpenSpec 組核對（2026-11-26），記入 `docs/alignment.md` 2026-11-26「001 學生身分改為同一瀏覽器共用」一列。

## Clarifications

### Session 2026-11-26

- Q: 學生的瀏覽器身分是否要求頁面上的 JavaScript 讀不到（限定 HttpOnly cookie），還是允許 localStorage 這類頁面讀得到的方式？ → A: 限定 HttpOnly cookie；學生端 HTTP 與即時推送連線都改由後端從 cookie 讀取身分，頁面不再自行附上學生 token。
- Q: 學生把瀏覽器整個關掉、之後再打開時，學生身分要不要保留？ → A: 保留；cookie 持續有效到離開本組、組別被刪除或活動失效為止，另設 1 天到期作為保險。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 同一瀏覽器只能代表一個組別 (Priority: P1)

學生在一個瀏覽器加入第 3 組後，這個瀏覽器在這個活動裡就是第 3 組。之後在同一個瀏覽器開新分頁、重新整理，或關掉分頁再打開學生頁，看到的都是第 3 組，不需要也不能再輸入組號。想在同一個瀏覽器另開分頁加入第 5 組（例如搶先佔用還沒有人加入的組號），系統會拒絕並提示「這個瀏覽器已是第 3 組成員，請先離開本組」。

**Why this priority**: 001 目前每個分頁都是一台獨立裝置，一個學生只要在同一台電腦開很多分頁，就能佔據多個組號或冒充他組的首位加入者，直接破壞搶答公平性。這是本子功能的核心。

**Independent Test**: 在瀏覽器甲的分頁 A 加入第 3 組，再於同一瀏覽器開分頁 B、C 進入同一活動的學生頁，確認 B、C 直接顯示第 3 組身分；在分頁 B 嘗試加入第 5 組，確認被拒絕、第 5 組沒有被建立。再用另一個瀏覽器（或另一台裝置）加入第 5 組，確認可以成功。

**Acceptance Scenarios**:

1. **Given** 活動在開放加入，瀏覽器甲的分頁 A 已加入第 3 組，**When** 在瀏覽器甲開新分頁 B 進入同一活動的學生頁，**Then** 分頁 B 直接顯示第 3 組身分、目前階段與本組加入憑證，不顯示加入表單。
2. **Given** 瀏覽器甲已是第 3 組成員，**When** 第 3 組的同學在**另一個瀏覽器**附上正確憑證加入第 3 組，**Then** 加入成功，兩個瀏覽器共用第 3 組的組別身分與已提交狀態（沿用 001 US2-AS2）。
3. **Given** 瀏覽器甲已是第 3 組成員，**When** 從瀏覽器甲的任何分頁送出加入第 5 組（或任何組別）的請求，**Then** 系統拒絕並說明「這個瀏覽器已是第 3 組成員，請先離開本組」；第 5 組不被建立、不發出任何憑證，第 3 組身分不變。送出的分頁顯示這則訊息後切換到第 3 組畫面。
4. **Given** 某請求帶著被竄改、過期或屬於其他活動的瀏覽器身分，**When** 它要求查看本組資料或提交，**Then** 系統視為沒有身分並拒絕，回應不含任何組別憑證或他組資料；頁面回到加入畫面（活動已失效時改顯示活動已失效）。
5. **Given** 瀏覽器甲已是第 3 組成員，**When** 學生關閉所有分頁（或整個瀏覽器）後，在同一個瀏覽器重新打開學生頁，並以帶活動代碼的網址進入，或在加入畫面輸入同一個活動代碼（組號任填）送出，**Then** 身分自動恢復為第 3 組，不需要知道原組號或憑證；以加入畫面送出時，同時顯示 AS3 的訊息。
6. **Given** 瀏覽器甲已是第 3 組成員，**When** 任一分頁送出提交且請求中自稱是第 5 組，**Then** 提交仍歸屬第 3 組（沿用 001 FR-012，組別由後端依瀏覽器身分判定）。

### User Story 2 - 同一瀏覽器的分頁狀態同步 (Priority: P1)

同一個瀏覽器開著多個學生分頁時，任何一個分頁的身分變化（加入、離開本組、組別被老師刪除、活動失效）都會在兩秒內反映到其他分頁，不會有某個分頁還以為自己是第 3 組、另一個分頁已經回到加入畫面的情況。

**Why this priority**: 身分改成整個瀏覽器共用後，若分頁畫面不同步，學生會在過期的畫面上操作而收到難懂的錯誤，甚至以為自己還能作答；這與 US1 同為上線必要條件。

**Independent Test**: 在同一瀏覽器開分頁 A、B，都停在加入畫面。在 A 加入第 3 組，確認 B 兩秒內自動切到第 3 組畫面；再在 B 按「離開本組」，確認 A 兩秒內回到加入畫面。最後由老師刪除組別、重啟後端，確認兩個分頁都正確更新。

**Acceptance Scenarios**:

1. **Given** 瀏覽器甲的分頁 A、B 都停在同一活動的加入畫面，**When** 分頁 A 加入第 3 組成功，**Then** 分頁 B 在兩秒內自動顯示第 3 組身分，不需要手動重新整理。
2. **Given** 瀏覽器甲的分頁 A、B 都顯示第 3 組，活動在開放加入、結果未定案或結果已定案，**When** 在分頁 B 按「離開本組」，**Then** 分頁 A、B 都在兩秒內回到加入畫面；第 3 組的其他瀏覽器、提交與成功次數不變（沿用 001 FR-034）。
3. **Given** 活動在搶答中，**When** 任一分頁要求離開本組，**Then** 系統拒絕（沿用 001 US7-AS3），所有分頁的身分都不變。
4. **Given** 瀏覽器甲的分頁 A、B 都顯示第 3 組，第 3 組從未提交，**When** 老師刪除第 3 組，**Then** 分頁 A、B 都在兩秒內回到加入畫面並看到「此組已被老師刪除」（沿用 001 FR-035）。
5. **Given** 瀏覽器甲的分頁 A 在搶答中送出第 2 題的答案，**When** 提交被接受，**Then** 分頁 B 在兩秒內顯示第 2 題已送出（沿用 003 同組多裝置的已提交狀態）。
6. **Given** 瀏覽器甲有兩個分頁顯示第 3 組，**When** 後端重新啟動，**Then** 兩個分頁都顯示「活動已失效，請重新建立或加入活動」，瀏覽器保存的舊身分不再被使用（沿用 001 FR-029）。

### User Story 3 - 老師與學生在同一瀏覽器時互不干擾 (Priority: P2)

老師在課堂上通常只用自己的瀏覽器，但測試或示範時可能在同一個瀏覽器同時開老師頁與學生頁。學生身分改成整個瀏覽器共用後，學生的加入、離開與老師身分必須互不影響，學生身分也不能被拿來做老師操作。

**Why this priority**: 001 曾發生學生分頁離開本組時清掉老師身分的問題（Issue #29）；本子功能改變身分的保存範圍，必須確保不再引入同類問題。但它不影響正式課堂的主流程，所以排在 P2。

**Independent Test**: 在同一個瀏覽器建立活動（老師頁），再開學生頁加入第 1 組、離開、再加入；每一步之後確認老師頁仍能開放加入、開輪與刪除組別。

**Acceptance Scenarios**:

1. **Given** 瀏覽器甲建立了活動 K 並開著老師頁，**When** 在瀏覽器甲開學生頁加入活動 K 的第 1 組，**Then** 加入成功，老師頁的老師身分與控制權不變。
2. **Given** 承上，**When** 學生頁按「離開本組」或第 1 組被老師刪除，**Then** 只有學生身分被解除，老師頁仍保有老師身分。
3. **Given** 瀏覽器甲只有學生身分，**When** 送出任何老師專用操作，**Then** 系統拒絕（沿用 001 US1-AS4），狀態不變。

---

### Edge Cases

- **不同瀏覽器或另一台裝置**：各自是不同的學生身分，可以加入不同組別（例如同組同學用手機與筆電各自加入同一組，或兩個組各用一台電腦）。本子功能只限制「同一個瀏覽器」。
- **同一台電腦用不同瀏覽器、無痕視窗或不同的瀏覽器設定檔**：會被視為不同的瀏覽器，仍能各自加入一組。本子功能的目標是**提高**佔用他組身分的難度，不是完全防止；這個限制寫在 Assumptions。
- **清除瀏覽器資料**：視同這個瀏覽器失去身分（沿用 001 Edge Case「同組所有裝置都失去身分」）：系統仍視原本的成員屬於該組，組別與憑證不變；學生要附憑證重新加入。清除後**不會**自動釋放組號，因此不能用「清資料 → 換組」繞過搶答中禁止換組的規則（搶答中清資料後加入他組，仍須該組憑證）。
- **同一瀏覽器加入不同活動**：學生身分以「瀏覽器 + 活動」為單位。同一個瀏覽器可以在活動 K 是第 3 組、在活動 M 是第 5 組；各活動互不影響。
- **兩個分頁幾乎同時加入不同組別**（分頁 A 加入第 3 組、分頁 B 加入第 5 組，兩個請求同時送出）：最多只有一個成功，另一個被拒絕並提示「這個瀏覽器已是第 N 組成員」；被拒絕的組號不被建立、不發出憑證。兩個分頁最後都顯示成功的那一組。
- **兩個分頁同時離開與提交**：搶答中離開一律被拒絕（001 FR-034），因此不會發生「提交送出的同時身分被解除」；其他階段沒有提交。
- **舊分頁在身分改變後才送出操作**（分頁 A 已離開本組，分頁 B 還沒更新就按下送出）：系統依當下的瀏覽器身分判定，沒有身分即拒絕並把分頁 B 帶回加入畫面，不會把操作算到已離開的組別。
- **瀏覽器拒絕保存身分資料**（例如封鎖網站資料）：無法保存身分時，加入請求 MUST 被拒絕，畫面明確提示「瀏覽器沒有保存身分，請允許本網站儲存資料後重新整理頁面。」，不得假裝已加入，也不建立組別。
- **網址帶著不存在的活動代碼**（例如貼錯連結）：這個分頁先前沒有成功同步過時，顯示加入畫面並提示「找不到這個活動代碼，請確認後再輸入。」（與 001 相同）；先前同步過、之後才不存在（後端重啟）時，才顯示「活動已失效」。
- **輸入驗證失敗時（憲章原則 V）**：適用的輸入為瀏覽器身分本身（以及 001 原有的活動代碼、組號、加入憑證）。格式錯誤、竄改、過期或屬於其他活動的身分一律視為沒有身分，不產生任何狀態變更；錯誤訊息只告訴學生「請重新加入」或「活動已失效」，不包含身分內容、憑證、堆疊追蹤或檔案路徑；身分內容不得出現在網址、畫面或日誌。

## Requirements *(mandatory)*

### Functional Requirements

**身分範圍**

- **FR-001**: 學生身分 MUST 以「瀏覽器 + 活動」為單位：同一個瀏覽器的所有分頁在同一活動中 MUST 共用同一個學生身分，取代 001 的「每個分頁是一台獨立裝置」。001 規格中所有「裝置」的規則（加入、憑證、離開、刪除、組號釋放、中途加入）改以瀏覽器為單位套用。
- **FR-002**: 不同的瀏覽器或裝置 MUST 仍是不同的學生身分，可以依 001 規則加入同一組或不同組。
- **FR-003**: 已有某組身分的瀏覽器，從任何分頁送出的加入請求（不論組號）MUST 被拒絕，並提示「這個瀏覽器已是第 N 組成員，請先離開本組」；被拒絕的請求 MUST NOT 建立組別、發出憑證或改變任何狀態。這項判定 MUST 由後端依瀏覽器身分完成，不依賴頁面自行檢查。
- **FR-004**: 學生身分 MUST 在同一瀏覽器的重新整理、新分頁、關閉分頁後重開，以及整個瀏覽器關閉後重開時自動恢復，直到學生離開本組、組別被刪除或活動失效為止；保存期限為最後一次開啟學生頁起 1 天（每次開啟學生頁都重新計算），到期後視為沒有身分（Clarifications 2026-11-26；滑動期限見 verification P-08）。
- **FR-005**: 每個請求所屬的組別 MUST 由後端依瀏覽器身分判定（沿用 001 FR-012），MUST NOT 採信請求中自稱的組號。
- **FR-006**: 離開本組（001 FR-034）與老師刪除組別（001 FR-035）MUST 解除整個瀏覽器在該活動的學生身分，該瀏覽器的所有分頁都 MUST 回到加入畫面。001 FR-034 的「離開的是該組最後一台裝置」改為「最後一個瀏覽器」。
- **FR-007**: 同一瀏覽器的兩個分頁同時送出加入請求時，系統 MUST 只讓其中一個成功；其餘 MUST 依 FR-003 拒絕。

**安全與驗證**

- **FR-008**: 瀏覽器身分 MUST 由系統產生、無法從活動代碼、組號或憑證推導；格式錯誤、竄改、過期或屬於其他活動的身分 MUST 視為沒有身分。身分內容 MUST NOT 出現在網址、頁面畫面、錯誤訊息或日誌中，也 MUST NOT 被頁面上的程式碼讀出或輸出（憲章原則 V；不得記錄 token）。瀏覽器身分 MUST 以 HttpOnly cookie 保存，由瀏覽器自動附在學生的每個請求與即時推送連線上，後端從 cookie 判定請求者；頁面 MUST NOT 自行在請求中附上學生身分（Clarifications 2026-11-26）。
- **FR-009**: 學生身分與老師身分 MUST 分開保存、各自解除：學生的加入、離開或組別被刪除 MUST NOT 影響同一瀏覽器的老師身分；學生身分 MUST NOT 取得任何老師專用權限（沿用 001 FR-003、US1-AS4）。

**同步**

- **FR-010**: 同一瀏覽器任一分頁的學生身分變化（加入、離開、組別被刪除）MUST 在兩秒內反映到該瀏覽器開著同一活動學生頁的所有其他分頁，不需要手動重新整理（與 001 FR-026 相同的兩秒標準，在正常本機連線、分頁於前景的情況下）。
- **FR-011**: 後端重啟後，帶舊瀏覽器身分的所有分頁 MUST 顯示「活動已失效」（沿用 001 FR-029），舊身分 MUST NOT 被套用到同代碼的新活動。
- **FR-012**: 分頁以已失效的身分送出操作時（例如另一分頁剛離開本組），系統 MUST 拒絕並讓該分頁回到加入畫面，MUST NOT 把操作算到原組別。
- **FR-013**: 瀏覽器無法保存身分時，加入請求 MUST 被拒絕且不建立組別，頁面 MUST 顯示「瀏覽器沒有保存身分，請允許本網站儲存資料後重新整理頁面。」，MUST NOT 顯示為已加入。

### Key Entities *(include if feature involves data)*

- **瀏覽器身分（Browser Identity）**：取代 001 的「裝置身分（Device Identity）」在學生端的意義。由系統發給一個瀏覽器、在某活動中指向某一個組別；同一瀏覽器的所有分頁共用；重新整理與重開分頁後恢復；離開本組、組別被刪除或後端重啟時失效。屬性：所屬活動、所屬組別、是否有效。實作上由兩部分組成：瀏覽器保存的「瀏覽器金鑰」（cookie，每個瀏覽器一把），以及後端在各活動中以金鑰雜湊為鍵的 001 `DeviceIdentity`（見 data-model.md）。
- **組別（Group）**：沿用 001，成員從「裝置」改為「瀏覽器身分」；「最後一台裝置離開時釋放組號」改為「最後一個瀏覽器身分離開時」。
- **老師身分（Teacher Identity）**：沿用 001，與瀏覽器身分分開保存、互不影響。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在同一個瀏覽器開 10 個分頁，各自嘗試加入不同組號，結果只有 1 個組別被建立，其餘 9 次 100% 被拒絕且沒有發出任何憑證。
- **SC-002**: 同一瀏覽器的 2 個分頁同時送出加入不同組號的請求，重複 20 次，每次都恰好 1 個成功，被建立的組別數每次都是 1。
- **SC-003**: 同一瀏覽器開 3 個分頁時，加入、離開、組別被刪除這三種變化，在其餘分頁畫面上 100% 於兩秒內反映。
- **SC-004**: 竄改、過期或其他活動的瀏覽器身分，對查看本組資料、提交、離開本組各嘗試一次，100% 被拒絕，回應中出現組別憑證、身分內容或他組資料的次數為 0。
- **SC-005**: 同一瀏覽器的學生頁做加入、離開、組別被刪除各一次後，老師頁的老師專用操作 100% 仍可使用。
- **SC-006**: 老師加上 6 組學生（每組 2 個瀏覽器）同時連線時，狀態變更仍在 2 秒內反映到所有畫面（沿用 001 研究 R2 的效能驗證條件，改為每組 2 個瀏覽器而不是 2 個分頁）。
- **SC-007**: 執行階段日誌與所有回應中，瀏覽器身分內容出現的次數為 0。

## Assumptions

- **目標是提高難度，不是完全防止**：同一個人用不同瀏覽器、無痕視窗、不同瀏覽器設定檔、清除瀏覽器資料或另一台裝置，仍能取得新的學生身分。完全防止需要學生帳號或實名登入，超出本專題範圍（系統只在本機執行、不做學生帳號）。已與 OpenSpec 組核對的範圍即為「同一瀏覽器」。
- **不以網路位址限制**：使用者描述提到「cookies 等網路資訊」。教室中學生常經由同一個網路出口連線，以網路位址判斷會把不同學生誤判為同一人，因此本子功能只使用瀏覽器保存的資料（例如 cookie）識別瀏覽器，不使用網路位址、裝置指紋等資訊。
- **保存方式**：瀏覽器身分以 HttpOnly cookie 保存（FR-008，Clarifications 2026-11-26）。cookie 改變不會通知其他分頁，因此 FR-010 這樣達成：加入時以同一瀏覽器內的分頁通知告知其他分頁（只傳活動代碼，不含身分內容）；離開本組與組別被刪除時，由既有的即時推送通知同一瀏覽器的所有連線；cookie 屬性與分頁通知機制的細節由 `/speckit-plan` 決定。學生可從瀏覽器開發者工具看到並複製 cookie，這屬於「提高難度、不完全防止」的範圍。系統只在本機以 HTTP 執行，因此不要求只能經由加密連線傳送。
- **保存期限**：瀏覽器身分保存到離開本組、組別被刪除或活動失效為止，瀏覽器整個關閉後重開仍保留（FR-004）；另設 1 天到期作為保險，一堂課不會超過這個長度。後端重啟後活動全部清空，舊身分自然失效。
- **對其他子功能的影響**：003 的提交、004 的排名與判錯、005 的寫回與 CSV 都以「組別」判定，不受「裝置 → 瀏覽器」的改變影響，程式行為不變。但 001、003、004、006 quickstart 與人工驗證步驟中「用多個分頁模擬多台裝置／多個組別」的寫法要改成「用不同瀏覽器或瀏覽器設定檔模擬」，於 `/speckit-tasks` 列為同步修改任務；自動化測試若以多個獨立連線模擬多台裝置，不受影響。
- **001 文件同步**：001 spec 的 FR-008、FR-009、FR-012、FR-034、US2、Key Entities「裝置身分」與 001 研究 R5 的「每個分頁是一台獨立裝置」，在本子功能實作時一併改寫或加註「由 007 修訂」，並同步 001 的圖表，維持憲章原則 II 的一致性。
- **老師端**：老師身分已是同一瀏覽器所有分頁共用（001 FR-003），本子功能不改變老師身分的規則，只確保學生身分與它互不影響。
