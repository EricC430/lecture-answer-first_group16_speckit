# 專案管理與版本管理規章

## 1. 目的與適用範圍

本規章適用於本專案所有組員，目的是讓需求、實作、審查及版本發布都有可追蹤的紀錄。工作以 GitHub 為協作中心，組員可使用 Claude 輔助實作，並依 Spec Kit 流程先定義規格再開發。最終的需求判斷、程式碼審查及合併責任仍由組員承擔。

## 2. GitHub 專案管理

### 2.1 Issue 與工作追蹤

- 每項功能、修正、文件工作或技術研究，原則上先建立 GitHub Issue；緊急修正可先處理，事後補建 Issue 並說明原因。
- Issue 應包含背景或問題、預期結果、驗收條件，以及必要的畫面、錯誤訊息或參考資料。
- 將 Issue 指派給主要負責人，並使用適當的標籤，例如 `feature`、`bug`、`docs`、`chore`。一個 Issue 以一項可驗收工作為原則。
- 使用 GitHub Projects（若已啟用）追蹤工作狀態：`Todo`、`In Progress`、`In Review`、`Done`。進度有變動時更新狀態；沒有啟用 Projects 時，以 Issue 狀態及指派資訊為準。
- 工作完成後，在 PR 關聯對應 Issue；合併時使用 `Closes #<issue-number>`，讓 GitHub 自動關閉已完成的 Issue。

### 2.2 分工與溝通

- 每項工作指定一位主要實作者；另一位組員負責審查。兩人應輪替實作者與審查者，避免長期由同一人包辦。
- 開始較大或可能影響既有功能的工作前，先在 Issue 說明方案及預計影響範圍；遇到需求不明、規格衝突或無法達成驗收條件時，先在 Issue 討論並取得共識。
- Claude 產生的程式碼、規格或文件必須由負責組員檢查、理解並驗證；不得將未理解或未測試的內容直接合併。

## 3. Claude 與 Spec Kit 開發流程

1. 從 GitHub Issue 確認需求、範圍及驗收條件。
2. 在 Claude Code 中使用已安裝在 `.claude/skills/` 的 Spec Kit skill（v1.2.1，skill 名稱為連字號格式），依序執行：`/speckit-constitution`（全專案一次）→ 每個子功能依序 `/speckit-specify` → `/speckit-clarify` → `/speckit-plan` → `/speckit-tasks` → `/speckit-analyze` → `/speckit-implement` → `/speckit-converge`。若 Spec Kit 版本升級造成命令不同，以環境提供者為準，並更新本文件。
3. 先檢查 Spec Kit 產生的規格與計畫是否符合 Issue；有歧義時先釐清，不直接讓 Claude 猜測需求。
4. 確認計畫後，再依任務使用 `/speckit-implement` 或 skill 提供的實作流程。實作期間遵守本文件的分支、提交及測試規則。
5. 完成後由組員檢視差異、執行適用的測試或檢查，並核對 Issue 的驗收條件；在 PR 描述中簡述使用 Claude／Spec Kit 的範圍，以及已執行的驗證。
6. Spec Kit 產生的規格與計畫若納入版本控制，應一併提交並在 PR 中說明；不得提交金鑰、個人資料或其他機密內容至 Claude 對話、Issue、PR 或 Git 儲存庫。

### 3.1 Spec Kit 使用慣例

- 憲章（`.specify/memory/constitution.md`）全專案共用一份，由兩位組員一起撰寫並經 PR 合併；修改憲章同樣走 PR，且須在 PR 說明影響哪些既有規格。
- 一個 Spec Kit 子功能對應一個 `specs/<編號>-<名稱>/` 目錄，內含自己的 spec、plan、tasks。切換子功能前，先確認 `.specify/feature.json`（本機狀態，不提交）指向正確目錄，避免把文件寫進別人的子功能。
- 子功能目錄編號由 Spec Kit 依序產生；為避免兩人同時建立而編號衝突，建立新子功能前先 `git pull` 並在 Issue 登記要用的編號與名稱。
- 分支名稱以第 4.1 節為準（含 Issue 編號）。Spec Kit 若自動建立 `NNN-name` 形式的分支，改以 `git branch -m` 重新命名，或在 specify 時指定分支名稱，使分支與 Issue 對應。
- `/speckit-implement` 完成後必須實際執行測試並記錄指令與結果數字，沒有執行就不得宣稱完成；`/speckit-analyze` 與 `/speckit-converge` 的結果需由審查者讀過。
- 規格、計畫與任務檔屬於課程評分標的，修改時保留可追溯的前因（Issue 或 PR 討論），不得為了讓檢查通過而事後改寫。

## 4. 分支與提交規則

### 4.1 分支策略

- `main` 是穩定且可整合的主要分支；不得直接在 `main` 上開發或提交。
- 每項工作由最新的 `main` 建立一條短期分支，完成後透過 Pull Request 合併。
- 分支名稱使用小寫英文及連字號，並包含類型與 Issue 編號：
  - `feature/12-add-quiz-timer`
  - `fix/18-correct-score-calculation`
  - `docs/21-update-workflow`
  - `chore/25-update-dependencies`
- 分支只處理其對應工作；若工作範圍改變，先更新 Issue 和 PR 說明。

### 4.2 Commit 規則

- 每個 commit 應代表一個清楚且相關的變更，避免混入無關格式調整或其他 Issue 的內容。
- Commit 訊息採用簡明的一行格式：`<type>: <summary>`。建議類型為 `feat`、`fix`、`docs`、`test`、`refactor`、`chore`。
- 範例：`feat: add quiz answer timer`、`fix: prevent duplicate submissions`。
- 不提交建置產物、暫存檔、個人設定或機密資訊；依專案 `.gitignore` 管理不應追蹤的檔案。

## 5. Pull Request 與程式碼審查

- PR 一律以 `main` 為目標分支，並在標題或說明中引用相關 Issue。
- PR 描述至少包含：變更目的與內容、關聯 Issue、驗收條件完成情形、測試／檢查結果，以及必要的畫面或操作說明。
- 作者應先自行檢查差異，確認沒有意外檔案、機密資訊、未完成標記或與需求無關的變更，並執行適用的測試及靜態檢查。
- 另一位組員需檢查需求符合度、程式正確性、可讀性、可能的回歸問題及驗證結果。作者不得自行核准自己的 PR。
- 審查者提出問題時，作者應修正或在 PR 討論中說明理由；修改後重新請審查者確認。取得至少一位非作者組員核准且必要檢查通過後，才可合併。
- 使用 GitHub 的 Squash and merge 合併 PR，維持 `main` 歷史清楚；如專案設定或課程要求另有規定，依共同決議調整。
- 合併後確認 Issue 關閉、分支刪除，並將 GitHub Projects 狀態更新為 `Done`（若有使用）。

## 6. 測試、整合與發布

- PR 必須通過專案已設定的自動化檢查；若目前沒有 CI，作者仍須在 PR 說明中記錄實際執行的測試或檢查。沒有適用測試時，說明人工驗證方式及結果。
- 合併前確認分支已包含最新 `main` 的必要變更，並處理衝突；不得以跳過必要檢查的方式掩蓋失敗。
- 對外展示或交付的穩定版本，由組員確認 `main` 狀態及驗收結果後建立 GitHub Release，使用 `vMAJOR.MINOR.PATCH` 標籤（例如 `v1.2.0`），並在 Release notes 摘要功能、修正及已知限制。
- 若專案尚未正式採用語意化版本，課程交付版仍至少使用可辨識且不重複的標籤；版本號規則如需變更，先取得組員共識。

## 7. 緊急修正與例外

- 若需立即修正已交付版本的重大問題，建立 `fix/` 分支及對應 Issue，優先修正並縮小 PR 範圍；仍須由另一位組員審查及驗證。
- 任何例外（例如暫時無法完成某項自動檢查）都必須在 PR 說明原因、風險及替代驗證方式，經另一位組員同意後才可合併；事後建立追蹤 Issue 補足欠缺工作。
- 本規章如需調整，應透過 PR 修改，並由兩位組員討論確認後合併。

## 8. 機敏資料與 AI 使用安全

- 密碼、金鑰、OAuth client secret、授權 token 一律不得出現在程式碼、文件、log、截圖、Issue、PR、commit 歷史或 Claude 對話中；只能放環境變數或本機未追蹤檔案，repo 只提供 `.env.example`（僅含變數名稱與假值）。
- 憑證檔、`.env`、`.claude/settings.local.json`、`CLAUDE.local.md` 等已列入 `.gitignore`；提交前以 `git status` 與 `git diff --staged` 確認沒有夾帶。
- 若機敏資料已被提交或推送，立即通知另一位組員、撤銷／更換該憑證，再清理歷史；撤銷優先於清理。
- 課程提供的作業說明 PDF 及其 Markdown 轉檔、提案草稿為本機參考資料，不追蹤、不上傳。
- 注意 AI 用量：日常以較低階模型處理文件整理與小修改，只有複雜規劃或除錯才改用較高階模型。

## 9. 驗證與品質關卡

- 「AI 自動驗證」與「人工驗證」缺一不可：每個子功能合併前，由非實作者依該子功能的驗收條件人工操作一次，並把步驟與結果寫在 PR（或該子功能目錄下的驗證紀錄）。
- 驗證紀錄須包含日期、實際執行的指令或操作、結果數字或截圖說明；對象要與這次改動對應，跑別的功能的結果不算。
- 測試預設不得呼叫真實外部服務；需要外部服務的測試要明確標記並說明前置條件，缺少條件時明確失敗而非略過。
- 規格、計畫、圖表、程式碼三者有任何一方改動，同一個 PR 內同步更新其餘部分；合併前檢查彼此一致。
- 繳交前一律以全新 clone 重跑一次安裝與測試，確認不依賴任何本機未提交檔案。

## 10. 跨小組協調與變更紀錄

- 本專案與另一小組（OpenSpec 組）須產出功能一致的系統，行為基準為 `docs/openspec-reference/`。
- **需要與對方討論的**：只有「重大功能性需求差異」，也就是新增、刪除或改變 OpenSpec 規格已規定的功能、規則或使用者可見行為，以及規格互相衝突、或模糊到會讓兩組做出不同功能的地方。這類事項先與對方討論，有共識後才實作偏離的部分。
- **不需要與對方討論的**：實作細節與設計方式（技術選型、元件與授權範圍、資料結構、畫面排版與文字措辭、檔案編碼與格式細節等），以及在 OpenSpec 規定範圍內的自行決定，由本組各子功能的 spec／plan 決定，不列入 `docs/alignment.md`。
- 規格有小的模糊、不影響功能一致時，spec 採 OpenSpec 原文字面解讀並寫在 Assumptions，不必逐項向對方提問；日後對方指出不同，再依實際差異修改。
- 需要討論的結果記錄於 `docs/alignment.md`：日期、議題、結論、影響範圍、確認狀態。口頭轉述的共識，記下日期與「口頭轉述」即算已記錄、可據以實作；確認人姓名選填，不因缺姓名而擋住實作。完全沒有記錄的口頭共識仍視為未確定。
- 對方小組要求的變更，同樣先在 Issue 評估影響範圍，再依第 3 節流程處理，不直接叫 Claude 修改。

## 11. 課程交付與時程管理

- 繳交期限為 2026-11-30（一）00:00；內部凍結時間定為 2026-11-29 晚上之前，凍結後只接受修正繳交阻礙問題的 PR。
- 交付物清單與負責人在 Issue 中追蹤：GitHub Repo、Demo 影片（5 分鐘內、上傳 YouTube）、AI 對話紀錄、系統簡述、實作方法與心得、小組分工表、組別評量表。
- AI 對話紀錄需持續保存：每個工作階段結束後匯出或保存 Claude 對話（先檢查並遮蔽機敏資料），按日期與子功能命名，存放於不入版控的本機資料夾或組員共用的私有位置，交付時統一彙整。
- 分工表與貢獻紀錄以 GitHub 的 Issue、PR、commit 為依據；每位組員都應有實作與審查的紀錄，避免交付時才回頭補寫。
- 影片錄製前先以乾淨環境走完整個展示流程一次（含老師端與至少兩個學生組別畫面），並鎖定該版本的 Git tag，確保程式碼、文件與影片一致。
- 加分項目（善用 branch 與 PR 協作、子功能拆分、額外功能）以實際的 GitHub 紀錄為證據，因此不得為了省事直接推送到 `main`。
